# 항공권 데일리 스캐너

청주 근처에 사는 사람이 **오늘 살 만한 항공권**을 5초 안에 고르기 위한 앱.

6시간마다(01·07·13·19시 KST) GitHub Actions 가 Travelpayouts 를 훑어 데이터를 만들고,
GitHub Pages 가 정적 앱으로 배포한다.

**핵심은 항공권 가격이 아니라 실부담가다.**

```
실부담가 = 항공권 가격 + 청주에서 그 공항까지 왕복 교통비
```

청주 350,000원 / 인천 230,000원 / 청주→인천 왕복 60,000원 이면
인천 실부담가가 290,000원이므로 **인천이 더 위에 온다.** 청주라서 무조건
우선하지 않는다.

## 구조

```
scanner.py                     수집 → 판정 → deals.json 생성 (데이터 전용)
web/index.html                 앱 셸
web/app.css                    디자인 시스템 (모바일 퍼스트)
web/app.js                     화면 · 실부담가 계산 · 설정
.github/workflows/daily.yml    매일 스캔 + Pages 배포
flight-deals/state/deals.json  화면이 읽는 단일 데이터 파일
flight-deals/state/brief.json  설정 없이 읽히는 아침 브리프용 요약
flight-deals/state/price_history.json   변동 추적 · 노선별 일별 최저가 · 얇은 버킷 표본
config/cjj_routes.json         청주 직항 노선 (운항 종료는 active:false)
```

**왜 HTML 을 파이썬이 굽지 않는가.** 교통비·출발지·특가 기준이 사용자
설정이고, 이 값이 바뀌면 실부담가와 순위가 통째로 달라진다. 빌드 시점에
HTML 로 굳히면 설정을 반영할 수 없다. 그래서 파이썬은 사실만 담은
`deals.json` 을 만들고, 순위는 화면에서 계산한다.

프레임워크는 쓰지 않는다. 바닐라 JS 한 파일이다.

홈에서 한 단계 아래로 내린 것: 전체 특가 리스트(전체 보기), 상세 화면,

총 얼마인가 / 평소보다 얼마나 싼가 / 표본이 충분한가.

## 국내 / 해외

홈 맨 위에 **전체 · 🇰🇷 국내 · ✈️ 해외** 3등분을 둔다. 출발지 칩보다 위에
두는데, 이쪽이 더 큰 구분이고 출발지는 그 안에서 다시 좁히는 것이기
때문이다.

**두 축은 완전히 다르다.**

| 축 | 무엇을 보나 | 어디에 |
|---|---|---|
| 국내/해외 (`S.scope`) | **도착지** — 어디로 가나 | `inScope()` |
| 출발지 칩 (`S.origin`) | **출발지** — 어디서 뜨나 | `inGroup()` |

곱해서 걸린다. "청주 + 해외" 같은 조합이 그대로 나온다.

```js
function originOffers() { return visibleOffers().filter(o => inGroup(o.dep, S.origin)); }
function homeOffers()   { return originOffers().filter(o => inScope(o, S.scope)); }
```

판정은 `region === '국내선'` 이 1순위다. 스캐너와 `config/cjj_routes.json`
이 같이 쓰는 값이라 화면이 따로 정의를 만들면 두 벌이 된다. `region` 이
비어 있는 옛 offer 를 위해 공항 코드(`KR_ARR`)로 한 번 더 받친다.
`tests/test_scope.py` 가 **config 의 국내선을 `KR_ARR` 이 전부 덮는지**,
**해외 노선이 거기 섞이지 않았는지** 를 매번 확인한다.

**0건인 칸도 지우지 않는다.** 칩마다 건수를 적고, 0이면 흐리게만 한다.
"오늘 국내는 0건" 도 정보다 — 칸을 없애면 왜 안 보이는지 알 수 없다
(월 칩과 같은 이유). 건수는 **스코프를 걸기 전** 풀(`originOffers()`)에서
센다. 걸고 나서 세면 고른 칩만 0이 아니게 되어 아무 정보도 못 준다.

같이 따라가는 것: 오늘의 강력 특가, 오늘 변화 타일, 월별로 보기,
청주 노선표, 씨앗 목록, 전체 특가 리스트. **화면 전체가 같은 말을 한다.**
스위스 탭은 원래 ZRH/GVA/BSL 전용이라 해당 없다.

### 타일 숫자는 누르면 열리는 목록에서 센다

예전에는 🆕 신규·📉 하락 타일이 `meta.stats`(전 노선 합계)를 적었다.
청주만 골라 놓고 타일을 누르면 숫자보다 적은 목록이 나왔다. 국내/해외를
넣으면 그 어긋남이 훨씬 커지므로 타일도 `homeOffers()` 에서 센다.

## 청주 전용 검색

**Travelpayouts 는 "CJJ 출발 전체"를 훑어주지 않는다.** 청주는 캐시가 얇아
출발지 단위로 물으면 몇 건 안 나온다. 그래서 청주만 **노선별로 직접 조회**한다.

운항 노선은 `config/cjj_routes.json` 이 관리한다. 22개 직항 목적지가 들어 있고,
운항이 끝난 노선은 **지우지 않고** `"active": false` 로 둔다. 지우면 그 노선의
price_history 를 다시 붙일 수 없다.

```json
"KIX": { "city": "오사카", "country": "일본", "flag": "🇯🇵",
         "region": "일본", "priority": 1, "active": true }
```

**호출은 노선당 1회다.** `length` 를 지정하지 않고 받은 뒤 실제 체류일로
1~10박만 거른다. 캐시가 얇은 곳에서 박수를 못 박으면 응답이 통째로 비기
때문이다 (스위스에서 실측). 출발일 창은 D+3~D+120.

priority 로 요일을 나눈다.

| priority | 노선 수 | 실행 |
|---|---|---|
| 1 | 11 | 매일 |
| 2 | 9 | 월·수·금 |
| 3 | 2 | 일요일 |

### 결과 없음 ≠ 운항 없음

**이 둘을 절대 섞지 않는다.** 운항 여부는 config 가, 가격 유무는 API 응답이
정한다. 가격이 안 나왔다고 노선을 목록에서 지우지 않는다.

| 필드 | 값 |
|---|---|
| `route_status` | `active` / `inactive` (config 가 결정) |
| `price_status` | `available` / `missing` / `error` (응답이 결정) |

화면에서도 `0원` 이나 `-` 로 적지 않는다.

```
오키나와 OKA     가격 데이터 부족
                 직항 운항 노선 · 최근 가격 없음
```

## 출발지별 수집 전략

**지방공항(CJJ·TAE·PUS)은 직항만 수집한다.** 설정의 환승 정책과 무관하게
수집 단계에서 걸러낸다. 청주에서 2회 환승 도쿄를 볼 이유가 없고, 환승편
가격이 섞이면 기준선까지 오염되기 때문이다.
(2026-08-30 실측: CJJ 10건 중 4건이 환승, 그중 2건은 2회 환승)

**캐시가 얇은 곳일수록 넓게 훑는다.** ICN 은 하루치로 버킷당 8건 안팎이
모이지만 CJJ 는 1~2건이라 같은 조건을 쓰면 기준선이 아예 안 만들어진다.

| 출발지 | 출발일 창 | 박수 | 환승 | 방식 |
|---|---|---|---|---|
| CJJ 청주 | D+3 ~ D+120 | 1~10박 | 직항만 | **22개 전 노선 매일** |
| TAE 대구 | D+3 ~ D+100 | 2~5박 | 직항만 | 출발지 단위 |
| PUS 부산 | D+3 ~ D+100 | 2~5박 | 직항만 | 출발지 단위 |
| ICN·GMP | D+3 ~ D+75 | 2~5박 | 설정에 따름 | 출발지 단위 |
| 스위스 | D+3 ~ D+180 | 2~21박 | **제한 없음** | 노선별 flex |

## 월별로 보기

"언제 가는 게 싼가" 는 이 앱에서 가장 자주 묻게 되는 질문인데, 리스트를
훑어야만 알 수 있었다.

- **홈 · 📅 월별로 보기** — 출발 월별 최저 실부담가와 건수. 누르면 그 달만
  걸린 리스트로 간다.
- **전체 특가 · 월 칩** — 등급 필터와 **다른 축**이다. "10월 강력특가" 처럼
  둘을 동시에 걸 수 있다.

두 곳의 건수는 같은 풀(`homeOffers()`)에서 센다. 다른 풀을 쓰면 홈에서
127건이라 눌렀는데 리스트는 126건인 일이 생긴다.

### 건수가 적은 달을 조심한다

달마다 수집 건수가 크게 다르다 (실측 9월 192건 · 12월 2건). 건수가 적은
달의 "최저가" 는 **그 달이 싸다는 뜻이 아니라 아직 데이터가 적다는 뜻**일 수
있다. 그래서 최저가만 크게 보여주지 않는다.

- 건수를 항상 같이 적는다
- `THIN_MONTH`(10건) 미만이면 목적지 대신 "표본 적음 · 참고만" 으로 바꾼다
- 💰 표시(가장 싼 달)는 얇은 달에는 붙이지 않는다

### 0건인 달도 지우지 않는다

월 칩은 **등급 필터를 걸기 전** 기준으로 만들고, 건수만 필터 후로 센다.
필터 후 기준으로 만들면 강력특가처럼 한 달에 몰린 조건에서 달이 하나만
남아 월 칩이 통째로 사라진다. 그러면 **"10월엔 강력특가가 없다" 는 사실이
보이는 대신 숨겨진다.** 0건인 달은 흐리게 표시하되 남긴다.

리스트는 120건까지만 그린다. 그래서 건수는 실제 매칭 수를 적고, 잘렸으면
"상위 120건 표시" 를 덧붙인다 — 127건을 120건이라고 적으면 거짓이다.

## 6시간마다 돈다

01 · 07 · 13 · 19시 KST (cron 은 UTC 라 `0 22,4,10,16 * * *`).

**왜 4배가 아닌가.** 소스는 사람들의 검색 캐시이고 보관이 2~7일이라
6시간마다 내용이 확 바뀌지는 않는다. 실제로 노리는 건 두 가지다.

- 잠깐 떴다 사라지는 값을 놓치지 않는다 (최저가 계열은 최근 48시간 캐시다)
- **가격의 나이를 24시간이 아니라 6시간 이내로 유지한다** (`found_at`)

한 번 실행에 실제로 쓰는 호출은 150~170회다(예산 260). 하루 4번이면
600~680회. 429 는 `call()` 이 두 번 재시도하고, 연속 6회 실패하면
서킷이 열려 그 실행을 중단한다.

### 하루 한 번을 전제로 짠 곳들

같은 날 다시 도는 게 처음이라, 다음 세 곳이 어긋날 수 있었다.

| | 문제 | 처리 |
|---|---|---|
| 기준선 표본 | 4배로 부풀면 특가 판정이 통째로 틀어진다 | **이미 안전.** 히스토리가 날짜 키로 *덮어쓰기*라 재실행이 표본을 늘리지 않는다 (`store[k][today] = ...`) |
| 그날 최저가 | 아침에 본 싼 값이 점심에 사라지면 최저가가 **올라간다** | `min(기존, 이번)` 으로 바꿨다. 최저는 내려가기만 한다 |
| 변동 배지 | "어제보다" 라고 써 놓고 실은 6시간 전과 비교 | 스캐너가 `delta_days` 를 계산해 넘긴다 |

`price_log` 는 계속 **하루 한 점**이다. 같은 날 다시 돌면 점을 늘리지 않고
그날 최저로 갱신한다 (`record_low` 가 이 값을 본다).

**`delta_days` 를 스캐너가 계산하는 이유.** 예전에는 브라우저가 로그 날짜
둘을 빼서 며칠 전인지 재고 있었다. 로그는 스캐너(KST)가 찍고 브라우저는
UTC 일 수 있어 하루씩 밀리는데, 6시간 주기에서는 **"오늘 앞선 조회" 를
"어제" 라고 부르는** 데까지 간다. 날짜 계산은 날짜를 찍은 쪽에서 한다.

### 커밋이 밀리는 것도 4배가 된다

`git push` 가 한 번 밀리면 스텝이 죽고 **deploy 까지 건너뛰었다.**
이제 리베이스로 세 번 시도하고, 그래도 안 되면 커밋만 포기하고 배포는
계속한다 — 데이터는 이미 파일에 있고, 이번 결과는 다음 실행에서 다시
커밋된다. 리베이스가 되려면 전체 클론이 필요해 `fetch-depth: 0` 을 켰다
(레포가 7MB 라 싸다). 커밋 메시지에는 날짜만이 아니라 시각도 적는다 —
하루 4개가 같은 이름이면 구분이 안 된다.

## 가격 변동 배지

`delta` = 이번 가격 − **직전에 기록된** 가격.

전에는 배지에 `📉 -2,754` 만 찍었다. 단위도 없고 무엇과 비교한 것인지도
없어서 읽을 수 없었다. 지금은 이렇게 적는다.

```
📉 어제보다 2,754원 내림
📈 3일 전보다 15,000원 오름
📉 직전 기록보다 5,000원 내림      ← 기록이 하나뿐이라 날짜를 모를 때
```

**날짜 차이는 로그끼리만 계산한다.** `Date.now()` 와 비교하면 안 된다 —
로그 날짜는 스캐너(KST)가 찍는데 브라우저는 UTC 일 수 있어서 하루씩
밀린다. 실제로 그렇게 만들었다가 "어제" 가 "2일 전" 으로 나오는 것을
UTC·KST·뉴욕 세 시간대로 확인하며 잡았다.

## 경유지 (`via`)

카드에 "1회 환승" 만 있고 **어디서 갈아타는지가 없었다.** 항공사도 `EY`
코드 그대로 나왔다.

**Travelpayouts 는 환승 횟수만 주고 경유 공항은 주지 않는다.** 지어낼 수
없으니 항공사 허브로 **추정**하되, 추정이라고 반드시 적는다.

| `via_src` | 뜻 | 표기 |
|---|---|---|
| `segment` | provider 가 준 **실제 구간** (Duffel) | `🔀 AUH 경유` |
| `hub` | 항공사 허브로 **추정** | `🔀 AUH 아부다비 경유(추정)` |
| `null` | 모름 | `🔀 2회 환승 · 경유지 미상` |

추정하지 않는 경우 — **모르는 것을 아는 척하지 않는다.**

- 직항, 환승 정보 없음
- **2회 이상 환승** — 허브 하나로 설명되지 않는다
- 허브를 모르는 항공사

허브가 둘인 항공사(루프트한자 FRA/MUC, 베트남 HAN/SGN)는 둘 다 적는다.
`AIRLINES` 에 외항사 한글명을 채웠다 (에티하드·중국동방·카타르…).

경유지는 **배지로 그린다.** 카드 부제 줄은 `text-overflow: ellipsis` 라
끝에 붙이면 잘려서 안 보인다 (소요시간 때 겪은 것과 같은 문제).

## "직항" 은 누가 한 말인가 (`stops_src`)

`/v1/prices/direct` 는 직항만 준다고 계약돼 있다. 예전 코드는 그 말을 믿고
응답 행의 환승 횟수를 **`stops = 0` 으로 덮어썼다.**

```python
# 예전 — 엔드포인트 이름을 근거로 값을 지어냈다
"number_of_changes": (forced_stops if forced_stops is not None
                      else r.get("number_of_changes")),
```

그런데 소스가 틀린 사례가 있다. **대구→괌**은 스카이스캐너에 "직항편을
운항하는 항공사는 없습니다" 라고 적혀 있는데도 대한항공 503,557원이
직항 −40% 특가로 잡혀 있었다. 우리 규칙 1번은 **가격을 지어내지 않는
것**이고, 직항 여부도 같은 무게의 사실이다.

그래서 값과 **그 값의 출처**를 나눈다.

| `stops_src` | 뜻 | 화면 |
|---|---|---|
| `row` | 응답 행이 환승 횟수를 직접 줬다 | 직항 |
| `endpoint` | 행에 값이 없고 엔드포인트 이름만 근거다 | **직항(소스 주장)** + "예약 전 확인" 배지 |
| `null` | 모른다 | 환승 정보 없음 |

**행과 엔드포인트가 어긋나면 행을 믿는다.** direct 엔드포인트가 준 행에
`number_of_changes: 1` 이 실려 있으면 `stops = 1`, `stops_conflict = true`
로 두고 화면에 **"⚠️ 소스 불일치"** 를 띄운다. 조용히 한쪽을 고르면 왜
이상한지 알 수 없게 된다. 불일치는 `meta.stops_conflict` 와 실행 로그에도
남는다.

부수 효과가 하나 있는데 이게 오히려 맞다: **지방공항 직항 필터**(`DIRECT_ONLY`)
가 이 값을 그대로 쓴다. 예전에는 `forced_stops=0` 덕에 환승편이 청주 직항
목록을 통과할 수 있었다. 이제는 걸러진다.

## 멀티 provider

Travelpayouts 는 캐시라 검색량이 적은 노선이 통째로 빈다. 그 구멍만 다른
provider 로 메운다. 데이터가 이미 충분한 노선에는 호출을 쓰지 않는다.

```
sources/base.py            Provider 추상 (예외 격리 · 토큰 없으면 비활성)
sources/travelpayouts.py   기존 fetch_route 를 감싸기만 한다
sources/duffel.py          실시간 offer. confidence A
sources/skyscanner.py      인터페이스만 확정 (구현 교체 가능)
core/normalize.py          공통 Offer 모델
core/merge.py              중복 병합 + 신뢰도 우선순위
core/quality.py            커버리지 지표 · A/B 리포트
```

### 신뢰도와 가격 등급은 다른 축이다

| | 뜻 | 값 |
|---|---|---|
| `source_confidence` | 얼마나 믿을 수 있나 | A(실시간 확정) · B(실시간/캐시) · C |
| deal tier | 얼마나 싼가 | 강력특가 · 특가 · 후보 · 일반 |

섞지 않는다. 실시간으로 확인된 비싼 표와 사흘 된 캐시의 싼 값은 서로 다른
이야기다. 화면에도 따로 표시한다 (`LIVE · Duffel` / `CACHE · Travelpayouts`).

**병합 대표는 가격이 아니라 신뢰도로 고른다.** 싼 캐시값이 실시간 확정가를
밀어내면 눌렀을 때 없는 가격을 보여주게 된다. 최저가는 `best_price` 로,
provider 별 값은 `sources[]` 로 함께 남긴다.

### fallback 발동 조건

```
CJJ 노선 → Travelpayouts 조회
         → 유효 왕복 5건(MIN_CJJ_ROWS) 이상이면 여기서 끝
         → 부족하면 Skyscanner 추가 조회 → merge → 직항 필터
```

**단순 row 수가 아니라 유효 왕복 수로 판단한다.** 원본 20건이 와도 전부
편도면 쓸 수 있는 가격은 0건이다.

ICN-ZRH 는 Duffel 우선(없으면 Skyscanner). 이코노미 · 왕복 · 최대 1회 환승 ·
4~14박. 날짜는 주 단위 seed 를 먼저 찍고 좋은 구간만 ±2일 넓힌다
(`SEED_STEP`/`SPREAD`) — 모든 날짜를 훑으면 호출이 폭발한다.

### 환경변수

| 변수 | 없으면 |
|---|---|
| `TP_TOKEN` | **스캔 실패** (기존 정책) |
| `DUFFEL_TOKEN` | Duffel 만 비활성 |
| `SKYSCANNER_API_KEY` | Skyscanner 만 비활성 |

부가 provider 의 토큰이 없다고 워크플로가 실패하지 않는다. provider 하나가
예외를 던져도 나머지는 계속 돈다.

### A/B 커버리지

`python scanner.py --ab` 로 `baseline.json` 과 비교한다. 평가 순서는 전체
건수가 아니라 **CJJ 0건 노선 수 → 가격 확인 목적지 수 → ZRH 유효 row →
ZRH 직항 → 전체** 다. 전체가 늘어도 0건 노선이 그대로면 실패다.

### 신규 노선 발견

`python scanner.py --discover` 는 후보를 `flight-deals/state/discovered_routes.json`
에만 적는다. **`config/cjj_routes.json` 을 자동으로 고치지 않는다.** 자동으로
active 를 켜면 운항하지도 않는 노선에 매일 호출을 쓰게 된다.

### 청주 직항은 매일 전부 본다

예전에는 priority 로 나눠 돌렸다 (1=매일, 2=월수금, 3=일요일). 예산이
빠듯했기 때문인데, 그 결과 **22개 중 13개만 보고** 히로시마·상하이·칭다오
같은 노선이 며칠씩 통째로 빠졌다. "청주 직항을 놓치지 않는다" 가 이 앱의
1번 목표인데 순번 때문에 못 보는 건 앞뒤가 안 맞는다.

예산을 호출 수 기준으로 다시 잡은 뒤(260) 전 노선을 매일 돌려도 최악의
경우 **180회**로 들어온다 (전 노선 0건 → 3차까지 가는 상황 시뮬레이션).
`priority` 값 자체는 지우지 않았다 — 노선이 더 늘어 예산이 빠듯해지면
다시 순번제로 돌릴 수 있어야 한다.

## 표본 누적

하루 표본이 **10건 미만인 (출발지·목적지·박수) 버킷**만 과거 가격을
누적해 기준선을 만든다. 보관 기간은 출발지별로 다르다.

`HISTORY_WINDOW` 로 공항별 기간을 정한다.

| 출발지 | 보관 |
|---|---|
| CJJ 청주 | 90일 |
| TAE·PUS | 45일 |
| ICN·GMP | 30일 |

ICN 은 하루치로 표본이 차므로 오래된 가격을 끌어오면 오히려 현재 시세를
흐린다. 그래서 30일로 짧게 둔다. 버킷이 두꺼워지면 누적을 버린다.

오늘 결과가 아예 없는 버킷은 되살리지 않는다 — 비교할 대상이 없다.
누적을 쓴 항공권은 카드에 **90일 누적 기준** 배지가 붙고, 상세 분석에서
어느 버킷이 누적을 썼는지 전부 볼 수 있다.

시뮬레이션(5일 연속 실행) 결과 CJJ 버킷 표본이
`[3~10]` → `[6~12]` 로 늘고, 기준선이 3단·2단에서 **전부 1단(노선·박수)** 으로
올라갔다.

## 특가 판정

**등급은 할인율과 표본 수를 함께 본다.** 표본 3건짜리 노선에서 "평균보다
60% 싸다"는 말은 평균이 곧 그 3건이라는 뜻이라 근거가 되지 못한다.

| 등급 | 조건 |
|---|---|
| 🔥 강력 특가 | 평균 대비 30%(설정) 이상 저렴 **AND** 표본 10건 이상 |
| 🟠 특가 | 20% 이상 **AND** 표본 5건 이상 |
| 🟡 특가 후보 | 10% 이상 표본 3건 이상, 또는 많이 싸지만 표본이 모자란 경우 |
| ⚪ 일반 | 그 외 |

표본 신뢰도: 10건+ 높음 / 5~9 보통 / 3~4 낮음 / 3 미만 참고.

DEAL SCORE(0~100)는 정렬에만 쓰고 화면에 숫자로 노출하지 않는다.
할인율 40 · 추적기간 최저 근접 15 · 실부담가 절대수준 15 · 직항 10 ·
신규 5 · 최근 하락 7 · 주말 적합 8 에 신뢰도 계수를 곱하고,
**출발 편의성 가산점**(`AIRPORT_BONUS`: CJJ +10 · TAE +3 · GMP +2 · ICN 0 · PUS −2)을
더한다. 가산점은 점수에만 들어가고 **화면의 실부담가는 실제 값 그대로**다.

정렬에는 타이브레이크가 하나 더 있다. 실부담가 차이가 **10,000원 이하**면
청주를 위로 올린다 — 이동시간·주차·출발 편의성 때문이다.

> 판정식은 `scanner.py` 의 `deal_tier()`/`deal_score()` 와
> `web/app.js` 의 `dealTier()`/`dealScore()` 에 **두 번** 적혀 있다.
> 파이썬 쪽은 설정 없이 읽히는 `brief.json` 전용이고, 화면 값은 항상 JS 가
> 사용자 설정으로 다시 계산한다. **한쪽을 고치면 다른 쪽도 같이 고쳐야 한다.**

## 가격 용어

같은 뜻처럼 보이는 말을 섞어 쓰지 않는다.

| 용어 | 뜻 |
|---|---|
| 오늘 최저가 | 이번 스캔에서 그 노선의 최저가 |
| 노선 평균가 | 이번 스캔의 그 노선 전체 평균 (박수 무관) |
| 비교 기준가 | 그 항공편의 할인율 판정에 실제로 쓴 값 |
| 최근 30일 최저 | 노선별 일별 최저가 30일 구간의 최저 |
| 추적 기간 최저 | 추적 시작 이후 전체 최저 |

비교 표현은 부호를 뒤집어 보여주지 않는다.
싸면 `평균보다 91,000원 저렴 ▼ 32%`, 비싸면 `평균보다 72,000원 비쌈 ▲ 18%`.
`절감 -72,000원` 같은 표기는 쓰지 않는다.

**비교 기준가는 3단으로 내려간다.** 노선·박수(표본 3+) → 노선 전체 박수(3+)
→ 목적지 기준·출발지 혼합(5+). 청주처럼 캐시가 얇은 출발지가 통째로
"비교 불가"로 빠지는 것을 막기 위한 것이고, 어느 단을 썼는지 상세 화면에
그대로 표시한다.

## 교통비 설정

초기값은 `scanner.py` 의 `ACCESS_COST` 이고, **설정 화면에서 공항별로 직접
고칠 수 있다.** 고치면 실부담가와 순위가 즉시 다시 계산되고
브라우저 localStorage 에 저장된다.

| 공항 | 초기값 (1인 왕복) |
|---|---|
| CJJ 청주 | 0원 |
| ICN 인천 | 44,000원 |
| GMP 김포 | 40,000원 |
| TAE 대구 | 30,000원 |
| PUS 부산 | 56,000원 |

**추정치다.** 이동수단·인원이 다르면 어긋난다. 그래서 항공권 실가격을
항상 같이 보여주고, 실부담가는 그 옆에 붙인다.

## 주말여행 조건

주말(토·일)이 걸리면서 **연차 0 / 0.5 / 1일**인 일정만 올린다.

- 토·일·공휴일은 연차로 세지 않는다. 월요일이 빨간날이면 토·일·월·화
  일정도 연차 1일이다.
- 출국일이 평일이면 출발 시각으로 나눈다: 20시 이후 0일(퇴근 후 탑승),
  18~20시 0.5일(반차), 그 외 1일.
- **귀국일은 항상 1일로 센다.** 캘린더 API 의 `return_at` 은 도착이 아니라
  현지 출발 시각이라 한국 도착 시각을 알 수 없다. 모르는 것을 유리하게
  반올림하지 않는다.

구간 탭: 이번 주말 / 다음 주말 / 9월 / 10월 / 연휴.

## 스위스 탐색 규칙

- **직항·1회 환승을 먼저 본다.** 2회 이상 환승은 목록에 남기되 대표편으로
  세우지 않는다. 값이 조금 싸다고 20시간짜리 2회 환승을 첫 화면에 올리면
  실제로 살 만한 편이 아래로 밀린다. 대신 **대표편 배지가 뽑힌 기준을
  말한다** — `💰 현재 최저가` / `🛫 직항 우선` / `✈️ 1회 환승 이내 최저가`.
  직항 우선으로 뽑았는데 "최저가" 라고 적으면 더 싼 편이 아래 있는데도
  이게 제일 싸다고 말하는 셈이다. 더 싼 편이 있으면 그 값도 같이 알린다.
- **취리히(ZRH)가 1순위다.** 화면은 항상 취리히 → 제네바(GVA) → 바젤(BSL)
  순서로 내려간다. 대표편도 이 순서로 고른다: 취리히에 편이 있으면 그중에서
  강력특가를, 없으면 취리히 최저가를 대표로 세우고, 취리히가 아예 비었을
  때만 제네바로 내려간다. **싼 제네바가 취리히를 밀어내지 않는다.**
- **환승 제한 없음.** 직항·1회·2회 이상을 전부 싣는다. 유럽은 캐시가 얇아서
  환승 횟수로 자르면 있는 것마저 사라진다. 설정의 환승 조건도 이 탭에는
  적용하지 않는다.
- 도시 안에서만 정렬한다: 직항 → 1회 → 2회 이상 → (환승 정보 없음),
  같은 그룹 안에서는 실부담가 → 여행 기간. 도시별로 🛫/✈️/🔁 로 묶어 보여준다.
- 가격이 없는 도시도 목록에서 지우지 않는다. "가격 데이터 부족"으로 남기고,
  **조회는 됐지만 왕복 확인 편이 없는 것**과 **응답 자체가 빈 것**을 구분해
  적는다. 어느 쪽도 "운항이 없다"는 뜻이 아니다.
- 근거리와 조건을 분리한다: 출발일 D+3~D+180, 체류 2~21박,
  `length` 를 지정하지 않고 한 번만 호출한 뒤 실제 체류일로 거른다

### 소스 3단계

얇은 노선은 소스를 단계적으로 늘린다. 앞 단계가 충분히 주면 뒷 단계는
호출하지 않는다.

| 단계 | 엔드포인트 | 조건 | 얻는 것 |
|---|---|---|---|
| 1차 | `/v1/prices/calendar` | 항상 | 출발일별 최저가 |
| **왕복** | `/aviasales/v3/prices_for_dates` | **유럽은 항상** | **`one_way=false` · 소요시간** |
| 2차 | `/v2/prices/latest` | 1차 5건 미만 | 최근 캐시 전체 |
| 3차 | `/v1/prices/cheap` | 2차까지 0건 | 다른 인덱스 (월 2회) |
| 3차 | `/v1/prices/direct` | 〃 | 직항만 — 나오면 `stops=0` 확정 |
| 3차 | `/v2/prices/month-matrix` | 3차 앞단이 3건 미만 | 월 단위 |

### 결론: 소스에 없다 (2026-08-30 확정)

여섯 엔드포인트를 다 붙이고 계측(`meta.v3`)까지 넣어 확인한 결과다.

| 노선 | v3 호출 | 원본 행 |
|---|---|---|
| ICN·SEL → GVA | 각 4회 | **각 1행** |
| ICN·SEL → ZRH | 각 4회 | **0행** |
| ICN·SEL → BSL | 각 4회 | **0행** |

에러 없음, 응답 필드도 문서와 일치(`price`/`airline`/`transfers`/`duration`).
**질의가 틀린 게 아니라 캐시에 없다.** 제네바 1행마저 이미 갖고 있던 그
3박짜리다.

Travelpayouts Data API 는 실시간 검색이 아니라 **남이 검색해서 캐시에 남은
값**을 준다. aviasales.com 웹 검색은 그때그때 항공사·GDS 를 찔러보는
메타서치라 결과가 다르다. 같은 회사 제품인데 우리가 쓸 수 있는 건 캐시
쪽뿐이다.

2026-08-30 실측: 이 앱이 만든 실시간 검색 링크로 연 화면에서
**ICN→ZRH 왕복 $614(에티하드, 1회 환승)** 가 나왔다. 우리 캐시에는 0건인
노선이다.

### 이름 없는 중복 (`merge_unnamed`)

`month-matrix` 와 `latest` 일부는 **항공사명을 주지 않는다**(`"?"`). 같은
항공편이 이름을 주는 엔드포인트에서도 오면 한 편이 두 줄이 된다.

2026-08-30 실측: 15개 일정에서 겹쳤고 가격 차는 **0.2~0.7%** 였다. 같은
편이다. 반면 진짜 다른 편은 **18~27%** 차이가 났다. 그래서 2%(`UNNAMED_TOL`)
를 경계로 잡고, 그 안에 드는 `"?"` 행은 버린다.

화면에 같은 편이 두 번 뜨는 것도 문제지만 **더 나쁜 건 표본 수가 부푸는
것**이다. 편 3개짜리 노선이 표본 6으로 보이면 "표본 충분" 판정이 잘못
내려간다. 실측에서 스위스 10행 → 5편, 전체 364 → 350건.

필드는 섞지 않는다. 싼 `"?"` 값에 항공사명을 붙이면 어느 응답에도 없던
항공권이 생긴다. 정보가 더 많은 쪽을 남길 뿐이다.

### 가격의 나이 (`found_at`)

이 소스는 **남이 Aviasales 에서 검색해서 캐시에 남은 값**을 준다. 보관은
쿼리 종류에 따라 2~7일이고, 최저가 계열은 "최근 48시간 안에 사용자가 찾은
값" 이다. 즉 **오늘 값과 사흘 전 값이 한 응답에 섞여 온다.**

`/v2/prices/latest` 와 `month-matrix` 는 `found_at` 을 준다. 이걸 버리면
둘을 같은 얼굴로 보여주게 되므로 그대로 싣고, 화면에 "N일 전 검색된 값"
배지로 적는다. 48시간이 넘으면 눈에 띄게 표시한다. 캘린더·v3 는 이 필드를
주지 않으므로 그때는 비운다 — 지어내지 않는다.

**따라서 내가 검색하면 캐시에 들어간다.** 원하는 노선이 비어 있으면 실시간
검색 링크로 한 번 검색해 두고 다음 스캔을 기다리는 것이 실제로 유효한
방법이다. 다만 보장은 아니다 — 캐시 반영 조건은 문서에 공개돼 있지 않다.

### 관심 노선 (`config/watchlist.json`)

새 목적지를 추가할 때 코드를 고칠 필요는 없다. 이 파일에 넣으면 매일
스캔에 자동으로 들어간다.

```json
{ "from": "ICN", "to": "LIS", "city": "리스본", "region": "유럽", "active": true }
```

`region` 을 `"유럽"` 으로 두면 장거리 규칙을 쓴다 (왕복 전용 소스 v3 항상
사용, 체류 2~21박, 출발일 D+3~D+180, 편도 별도 수집).

**등록만으로는 안 채워진다.** 이 소스는 사람들의 검색 기록이라, 아무도
검색하지 않는 노선은 계속 0건이다. 순서는 이렇다.

1. `watchlist.json` 에 노선을 추가한다
2. 앱의 "실시간으로 검색하기" 버튼으로 **한 번 직접 검색한다**
3. 그 다음 스캔부터 자동으로 추적된다

사람이 하는 건 2번 한 번뿐이고, 그 뒤로는 전부 자동이다.

> **자동 검색(봇)은 하지 않는다.** Travelpayouts 는 실시간 검색을 MAU 50,000
> 이상 파트너에게만 연다. 소비자 사이트를 봇으로 돌려 같은 데이터를 얻는 건
> 그 제한을 우회하는 것이고, 계정·토큰이 정지될 위험이 있다. GitHub Actions
> 는 데이터센터 IP라 차단도 거의 확실하다.

쓰지 않게 된 노선은 지우지 말고 `"active": false` 로 둔다. 지우면
`price_history` 의 과거 가격과 연결이 끊긴다.

### 0건이 아니라고 채워진 게 아니다 (`thin`)

씨앗 목록은 원래 **"가격이 0건이냐"** 만 봤다. 그래서 취리히는 3건이 있다는
이유로 목록에서 빠졌는데, 특가 판정에는 **표본 10건**이 필요하다.

| | 표본 | 판정 |
|---|---|---|
| 취리히 ICN-ZRH | **3건** | 아무리 싸도 '강력 특가' 가 안 붙는다 |
| 바젤 ICN-BSL | 0건 | 비교 자체가 없다 |

둘 다 못 쓰는데 목록에는 바젤만 있었다. `SEED_THIN_N`(=10, `dealTier` 의
강력특가 기준과 **같은 숫자**)보다 적으면 `thin` 으로 같이 올린다.
`tests/test_seed_thin.py` 가 두 숫자가 어긋나지 않는지 확인한다.

**취리히가 맨 위다.** 0건인 바젤보다 3건인 취리히를 먼저 채우는 게 맞다 —
실제로 가려는 곳이 취리히이기 때문이다 (스위스 탭의 1순위 규칙과 같은 말).

**표본이 얇다고 다 사람 손이 필요한 건 아니다.** 제주·도쿄처럼 매일 가격이
들어오는 노선은 며칠 두면 저절로 10건이 된다. 손이 필요한 건 아무도 안
찾아서 스스로는 절대 안 차는 노선(스위스)뿐이다. 안 가르면 목록이 24줄이
되어 아무도 안 누른다. 저절로 차는 쪽은 **숨기지 않고 한 줄로** 적는다 —
"9곳은 표본이 모자라지만 저절로 찹니다. 손댈 필요 없습니다."

**이미 가진 날짜를 또 검색하라고 하지 않는다.** 취리히 3건은 전부
10/29~11/01 한 구간에 몰려 있어서, 거기서 또 찾아 봐야 표본이 안 는다.
후보 날짜(`LIVE_OFFSETS` = D+45/75/105) 중 **가진 것과 가장 먼 날**을
고른다. 오늘을 UTC 자정으로 맞춰서 비교한다 — 브라우저 로컬시각과
스캐너(KST)가 찍은 날짜를 그냥 빼면 하루씩 밀린다. 테스트가 UTC ·
Asia/Seoul · America/New_York · Pacific/Kiritimati 에서 같은 답이
나오는지 확인한다.

### 비어 있는 노선을 채우는 법 (그리고 다시 비어지는 것)

이 소스는 사람들의 검색 기록이다. 그래서 노선이 두 종류로 갈린다.

| | 예 | 동작 |
|---|---|---|
| 많이 찾는 노선 | 도쿄·오사카·후쿠오카·제주 | 남들 검색으로 **저절로 채워진다** |
| 거의 안 찾는 노선 | 삿포로·발리·취리히 | 직접 한 번 검색해야 들어온다 |

2026-08-30 실측: 청주 13개 노선 중 **7개는 손대지 않았는데 채워져 있었다.**
직접 씨앗이 필요한 건 6개뿐이었다.

**다만 한 번으로 영원히는 아니다.** 캐시 보관은 2~7일이라, 계속 아무도 안
찾는 노선은 언젠가 다시 비어진다. 사용자가 그걸 기억하고 있으라고 하면
안 되므로 앱이 알려 준다.

- `route_freshness` (deals.json): 노선별 마지막으로 가격이 들어온 날과
  그 이후 며칠. **`route_stats` 는 오늘 offer 가 있는 노선만 만들어서
  끊긴 노선이 통째로 사라진다** — 그래서 별도로 계산한다.
- 청주 화면: 가격 없는 노선에 버튼. 기록이 없으면 "🔎 검색해서 채우기",
  들어왔다가 끊겼으면 "🔄 N일째 없음 · 다시 채우기"
- 버튼은 **실제로 조회했는데 빈 노선에만** 붙인다. priority 순번상 오늘
  안 본 노선에 "검색하라" 고 하면 헛수고를 시키는 것이다
- 스위스 탭도 같은 방식으로 마지막 수집일을 적는다

### 자동 검색(봇)은 만들지 않는다

Travelpayouts 는 실시간 검색 API 를 **MAU 50,000 이상** 파트너에게만 연다.
소비자 사이트(aviasales.com)를 헤드리스 브라우저로 돌려 같은 데이터를 얻는
것은 그 제한을 우회하는 것이다. 계정·토큰 정지 위험이 실재하고, Actions 는
데이터센터 IP라 차단도 거의 확실하다.

대신 **사람이 하는 부분을 최소로 줄인다.** 홈의 `🌱 비어 있는 노선 채우기` 가
씨앗이 필요한 노선을 한 자리에 모아 준다.

목록에 오르는 조건은 두 가지다.

| state | 뜻 | 표기 |
|---|---|---|
| `empty` | 가격이 아예 없음 | `검색하기 →` |
| `stale` | 가격은 있지만 `REFRESH_DAYS`(3일) 넘게 갱신이 멈춤 | `🔄 N일째 갱신 없음 · 새로고침 →` |

**비어버린 뒤에 올리면 이미 며칠을 놓친 뒤다.** 캐시는 2~7일이면 빠지므로,
아직 값이 남아 있어도 갱신이 멈췄으면 미리 올린다. 도쿄·오사카처럼 남들이
계속 검색하는 노선은 늘 0일이라 여기 걸리지 않는다.

- 누르면 aviasales 검색 화면이 열린다. **항공권 목록이 실제로 뜰 때까지
  기다려야 한다** — 결과가 나오기 전에 닫으면 검색이 끝나지 않아 기록이
  안 남을 수 있다
- 무엇을 눌렀는지 앱이 기억한다 (`localStorage`, 이 기기에만)

**"눌렀다" 와 "캐시에 남았다" 는 다르다.** 앱이 아는 것은 앞의 것뿐이므로
표시도 그렇게만 한다 — `오늘 열어봄 · 결과 대기`. 처음에는 `오늘 완료` 라고
적었는데, 검색이 끝까지 안 돌았어도 완료로 보여서 거짓이 될 수 있었다.

실제로 남았는지는 **다음 스캔이 답한다.** 채워지면 목록에서 사라지고,
내일도 남아 있으면 검색이 끝까지 안 돈 것이니 한 번 더 누르면 된다.

**앱 새로고침은 검색이 아니다.** 웹앱은 `deals.json` 파일 하나만 읽고
(`fetch('deals.json')`), Travelpayouts 주소를 코드에 갖고 있지도 않다.
스캐너의 API 호출도 캐시를 **읽기만** 한다. 캐시에 기록을 남기는 것은
실제 검색뿐이다.

### 실시간 검색 API 를 왜 안 쓰나 (2026-08 조사)

| 후보 | 상태 |
|---|---|
| Travelpayouts Flight Search API | **MAU 50,000 이상**만 승인. 미달이면 Data API 를 쓰라고 안내 |
| Kiwi.com Tequila | 2024-05-30 부터 **초대제**. 자체 가입 불가 |
| Amadeus Self-Service | **2026-07-17 종료**. 기존 키도 정지 |
| Duffel | 테스트는 무료지만 샌드박스 데이터. 실데이터는 계약 필요 |

개인 프로젝트가 붙일 수 있는 무료 실시간 소스가 없다. 그래서 구조를
이렇게 잡는다 — **캐시로 "어디가 쌀 때인지" 감을 잡고, 실제 예약은 실시간
검색으로 넘긴다.** 없는 노선은 "없다" 고만 말하지 않고 출발일 후보 3개를
버튼으로 준다 (`liveSearchHTML`, `LIVE_OFFSETS` D+45·75·105 × 10박).
가격은 출발일에 따라 크게 달라서 창을 하나만 주면 쓸모가 적다.

### 왕복을 달라고 말할 수 있는 곳은 하나뿐이다

`calendar`·`latest`·`cheap`·`direct`·`month-matrix` 다섯 곳 중 **어디에도
"왕복만 달라"는 파라미터가 없다.** 캘린더는 `length` 로 에둘러 요청하지만
그마저 무시당하고, 나머지는 캐시에 있는 걸 그냥 준다. 그 결과가 이것이었다.

- 제네바 왕복 6건이 **전부 3박** — 유럽을 3박으로 가는 사람은 없다.
  실제로 사는 7~14박이 통째로 빠져 있었다.
- 취리히 23건이 **전부 편도** — `cheap`·`direct` 에 `return_date` 를
  안 넘기면 이 API 들은 편도를 준다. 넘기도록 고쳤다.

`/aviasales/v3/prices_for_dates` 만 `one_way=false` 를 받는다. 유럽은
조건 없이 항상 이걸 붙인다. `duration`(분) 도 이 응답에만 있어서, 소요시간을
표시할 수 있는 편은 여기서 온 것뿐이다 — 없는 편은 비워 둔다.

3차 예산은 **노선 수가 아니라 호출 수**로 막는다(`DEEP_BUDGET`). 단계마다
호출 수가 달라서 "노선 4개까지" 로는 실제 지출을 통제할 수 없다. 유럽 밖은
지역별이 아니라 통짜 한 바구니다 — 청주가 지역을 5개 걸치고 있어서
지역별로 주면 합계가 걷잡을 수 없이 커진다.

### 편도 캐시

3차 소스를 붙였더니 취리히가 **원본 0건 → 23건**이 됐다. 그런데 23건 전부
`return_at` 이 없는 **편도**였다. 귀국일을 지어낼 수는 없지만, 버릴 것도
아니다 — 그게 그 노선에 존재하는 유일한 데이터다.

- **유럽만** 편도를 받는다 (`ALLOW_ONEWAY`). 근거리는 왕복 캐시가 충분해서
  편도를 섞을 이유가 없고, 섞으면 "싸 보이는" 편도가 목록을 오염시킨다.
- 편도는 `offers` 에 넣지 않는다. `deals.json` 의 **별도 배열 `oneway`** 로
  나간다. 기준선·평균가·특가 판정·순위는 전부 `offers` 만 보므로,
  구조적으로 섞일 수 없다. 편도 가격을 왕복 표본에 섞으면 노선 평균가가
  절반으로 내려앉아 멀쩡한 왕복이 전부 "평균보다 비쌈" 이 된다.
- 편도 행에는 `effective_krw`·`baseline` 필드가 **아예 없다**. 실부담가를
  계산하지 않는다.
- 화면에서도 `cardHTML` 을 쓰지 않는다. 점선 테두리 · "편도 · 가는 편만" ·
  "편도" 배지 · 그룹 위 경고문으로 왕복과 분리해 그린다.

- 같은 편이 `ICN→ZRH` 과 `SEL→ZRH` 로 두 번 들어온다 (API 가 둘 다 SEL 로
  접어서 답한다). 요청 코드가 아니라 **실제 편 기준**으로 묶고, 표시는
  구체적인 공항코드(ICN)를 남긴다. 실측 46건 → 23건.
- 정렬은 위쪽 왕복 그룹과 같은 규칙을 쓴다: 직항 → 환승, 그다음 값.

`tests/test_oneway_isolation.py` 가 이 분리와 중복 제거를 검증한다.

테스트는 전부 토큰 없이 돌아간다.

| 파일 | 검증 |
|---|---|
| `tests/test_v3_roundtrip.py` | `one_way=false` 를 실제로 넘기는지, 10·14박이 살아남는지, 달을 걸친 중복 제거, `duration` 수록 |
| `tests/test_deep_sources.py` | `cheap`·`direct` 에 `return_date` 를 넘기는지, 조기 종료, `direct`→`stops=0` |
| `tests/test_oneway_isolation.py` | 편도가 `offers`·기준선에 안 섞이는지, 도시코드 중복 제거 |
| `tests/test_budget.py` | 전 노선 0건인 최악의 경우 예산·상한 |

대표편 배지는 **특가일 때만 메달**을 붙인다. 표본이 있어도 등급이 '일반'이면
"🥇 일반" 이 되어 버리므로, 그 자리가 왜 1등인지를 그대로 부른다 —
스위스·홈 저가 폴백은 "💰 현재 최저가", 홈 특가 목록은 "🥇 오늘 1순위".

**총 여행시간과 환승 대기시간은 정렬에 넣지 못했다.** Travelpayouts 캘린더
응답에 그 필드가 없다. 화면에도 지어내지 않고, 없다고 적어 두었다.

강력 특가가 없어도 빈 화면으로 끝내지 않는다. 현재 가격 · 30일 최저 ·
추적기간 최저 · 평균가를 보여주고 "조금 더 기다려볼 만함"까지 판단해 준다.
응답 자체가 비면 노선별 원본 건수와 탈락 사유를 표로 보여준다.

## 알려진 한계

- **Travelpayouts 는 캐시 데이터다.** 실시간 확정 판매가가 아니다.
  예약 전 판매처에서 반드시 확인해야 한다.
- **교통비는 추정치다.** 1인 왕복 기준이라 인원·이동수단이 다르면 어긋난다.
  그래서 항공권 실가격을 항상 주 표기로 둔다.
- **공휴일 표는 수동 관리다.** 검색 창이 `HOLIDAYS` 의 마지막 날짜를 넘으면
  그 이후 연차 계산이 부정확해진다. 실행 로그와 `brief.json` 에 경고가 뜬다.
- **`duration` 은 왕복 총합이다.** 실측 2510분 = 41시간 50분. 이걸
  "비행시간" 으로 쓰면 편도 20시간짜리가 41시간으로 읽힌다. 가는 편은
  `duration_to` 로 따로 오므로 갈라 담고, 화면에도 "가는 편" / "왕복 합"
  으로 구분해 적는다.
- **소요시간은 일부 편에만 있다.** `/aviasales/v3/prices_for_dates` 응답에만
  `duration` 이 들어 있다. 있는 편만 배지로 표시하고 없는 편은 비워 둔다.
  **환승 대기시간은 어느 응답에도 없다** — 정렬 기준으로 쓰지 않는다.
- **취리히는 편도만 있다 (v3 투입 이전 기록).** 3차 소스 투입 후 ICN/SEL→ZRH 원본 46건이
  잡혔지만(중복 제거 후 23건) 전부 편도였다. 왕복 취리히는 다섯 엔드포인트
  어디에도 없다. 그중 직항 편도가 59만원대로 확인된다.
  바젤은 여전히 전 소스 0건이다.
- **취리히·바젤이 안 나온다 (3차 소스 이전 기록).** 2026-08-30 실측에서 ICN/SEL→ZRH·BSL 은
  `/v1/prices/calendar` 와 `/v2/prices/latest` **양쪽 모두 원본 0건**이었다.
  `one_way` 파라미터를 빼서 조건을 더 풀어 봐도 그대로였다. 우리 필터 탓이
  아니라 소스 캐시에 그 노선이 없는 것이다. 그래서 3차 소스 세 곳을 더
  붙였다 — 다음 스캔 결과를 봐야 한다. 화면의 "소스 N곳을 모두 확인했지만"
  문구는 `meta.deep_tried` 를 읽어 실제로 몇 단계까지 갔는지 말한다.
  어느 쪽이든 **운항이 없다는 뜻은 아니다.**
- **스위스 캐시가 거의 없다.** 2026-08-30 실측에서 ICN→ZRH·BSL 원본 0건,
  GVA 2건(3박 왕복)뿐이었다. 조회 실패가 아니라 소스에 데이터가 없는 것이고,
  화면에 노선별 원본 건수와 탈락 사유를 그대로 보여준다.
- **총 여행시간·환승 대기시간을 알 수 없다.** 캘린더 API 에 없다.
- **청주(CJJ) 캐시가 얇다.** ICN 대비 6% 수준이고 버킷당 1~2건이다.
  노선별 개별 조회 + 직항 강제 + 창 확대(D+120) + 90일 표본 누적 +
  3단 기준선으로 보강했다. 그래도 **가격이 안 잡히는 노선이 남는다.**
  그건 운항이 없는 게 아니라 소스에 가격이 없는 것이고, 화면에
  "가격 데이터 부족"으로 구분해 표시한다. 누적은 **과거 가격**이라 현재 시세와 차이가
  날 수 있어, 어느 단을 썼고 며칠치를 끌어왔는지 화면에 그대로 표시한다.
  실행 첫날은 누적할 과거가 없으므로 며칠 쌓여야 효과가 난다.
- `depart_date` 월 필터와 `one_way` 파라미터가 API 에서 무시된다.
  왕복 기간 통제는 `length` 가 담당하고 코드에서 박수를 다시 검증한다.
- API 가 공항코드를 도시코드로 접어 응답한다 (ICN→SEL, KIX→OSA).
  실제 편 기준으로 중복을 제거한다. 화면에서 `SEL` 은 서울권으로 묶는다.
- **설정은 브라우저에 저장된다.** 기기를 바꾸면 다시 설정해야 한다.
